================================================================================
  GUIDE COMPLET - DÉPLOIEMENT LARAVEL 10 SUR HOSTINGER VPS AVEC DOCKER
  Rédigé à partir du projet SAAHEEM - À réutiliser pour tout projet Laravel
================================================================================

Ce guide couvre tout le chemin : projet local → GitHub → Docker → Hostinger VPS
avec déploiement automatique à chaque git push sur main.


────────────────────────────────────────────────────────────────────────────────
1. PRÉREQUIS
────────────────────────────────────────────────────────────────────────────────

  Côté local :
  - Git installé
  - Docker Desktop installé (pour tester localement si besoin)
  - Compte GitHub avec un repo pour le projet

  Côté hébergement :
  - VPS Hostinger (plan KVM2 minimum recommandé)
  - Docker installé sur le VPS (Hostinger propose des VPS avec Docker pré-installé)
  - Un nom de domaine pointant vers l'IP du VPS (record A dans le DNS)

  Côté GitHub :
  - GitHub Container Registry (GHCR) activé (gratuit, inclus dans GitHub)
  - Actions activées sur le repo


────────────────────────────────────────────────────────────────────────────────
2. STRUCTURE DES FICHIERS DOCKER À CRÉER
────────────────────────────────────────────────────────────────────────────────

  Arborescence à ajouter à la racine du projet Laravel :

  projet/
  ├── Dockerfile
  ├── docker-compose.yml           ← pour tester en local
  ├── docker-compose.prod.yml      ← utilisé par GitHub Actions en prod
  ├── docker/
  │   ├── nginx/
  │   │   └── default.conf
  │   └── php/
  │       ├── php.ini
  │       ├── opcache.ini
  │       └── entrypoint.sh
  └── .github/
      └── workflows/
          └── deploy.yml

3. DOCKERFILE (multi-stage)
────────────────────────────────────────────────────────────────────────────────

  Le Dockerfile a 3 étapes (stages) :
  - Stage 1 (node-build) : compile les assets Vite (CSS/JS)
  - Stage 2 (app)        : PHP-FPM avec les dépendances Composer
  - Stage 3 (nginx)      : Nginx qui sert les fichiers statiques

  ── Dockerfile ──────────────────────────────────────────────────────────────

  # Stage 1 : build assets Vite
  FROM node:20-alpine AS node-build
  WORKDIR /app
  COPY package*.json ./
  RUN npm ci --prefer-offline
  COPY vite.config.js ./
  COPY resources ./resources
  COPY public ./public
  RUN npm run build

  # Stage 2 : PHP-FPM production
  FROM php:8.2-fpm-alpine AS app
  RUN apk add --no-cache libpng-dev libjpeg-turbo-dev freetype-dev zip unzip \
      && docker-php-ext-configure gd --with-freetype --with-jpeg \
      && docker-php-ext-install -j$(nproc) gd opcache
  COPY docker/php/opcache.ini /usr/local/etc/php/conf.d/opcache.ini
  COPY docker/php/php.ini     /usr/local/etc/php/conf.d/app.ini
  COPY --from=composer:2 /usr/bin/composer /usr/bin/composer
  WORKDIR /var/www/html
  COPY composer.json composer.lock ./
  RUN composer install --no-dev --no-interaction --prefer-dist \
      --optimize-autoloader --no-scripts
  COPY . .
  COPY --from=node-build /app/public/build ./public/build
  RUN chown -R www-data:www-data storage bootstrap/cache \
      && chmod -R 775 storage bootstrap/cache
  RUN mkdir -p storage/framework/views storage/framework/cache \
              storage/framework/sessions storage/logs \
      && php artisan package:discover --ansi \
      && php artisan route:cache \
      && php artisan view:cache
  COPY docker/php/entrypoint.sh /entrypoint.sh
  RUN chmod +x /entrypoint.sh
  EXPOSE 9000
  ENTRYPOINT ["/entrypoint.sh"]
  CMD ["php-fpm"]

  # Stage 3 : Nginx
  FROM nginx:1.27-alpine AS nginx
  COPY --from=app /var/www/html/public /var/www/html/public
  COPY docker/nginx/default.conf /etc/nginx/conf.d/default.conf
  EXPOSE 80

  ────────────────────────────────────────────────────────────────────────────

  POURQUOI 3 STAGES :
  - L'image finale app ne contient pas Node.js (plus légère)
  - L'image nginx est minimale et séparée de PHP
  - En prod, les deux images sont indépendantes et peuvent redémarrer séparément


────────────────────────────────────────────────────────────────────────────────
4. DOCKER/NGINX/DEFAULT.CONF
────────────────────────────────────────────────────────────────────────────────

  server {
      listen 80;
      server_name _;
      root /var/www/html/public;
      index index.php;
      charset utf-8;

      # Fichiers statiques servis directement par Nginx avec cache 30 jours
      location ~* \.(jpg|jpeg|png|gif|webp|mp4|webm|mov|ico|css|js|woff2?|ttf|svg)$ {
          expires 30d;
          add_header Cache-Control "public, immutable";
          try_files $uri =404;
      }

      location / {
          try_files $uri $uri/ /index.php?$query_string;
      }

      location ~ \.php$ {
          fastcgi_pass   app:9000;   # "app" = nom du service dans docker-compose
          fastcgi_index  index.php;
          fastcgi_param  SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
          include        fastcgi_params;
          fastcgi_read_timeout 60;
      }

      location ~ /\.(env|git|htaccess) {
          deny all;
      }

      client_max_body_size 50M;
  }


────────────────────────────────────────────────────────────────────────────────
5. DOCKER/PHP/ENTRYPOINT.SH
────────────────────────────────────────────────────────────────────────────────

  #!/bin/sh
  set -e
  mkdir -p storage/framework/views storage/framework/cache \
           storage/framework/sessions storage/logs
  chown -R www-data:www-data storage bootstrap/cache
  chmod -R 775 storage bootstrap/cache
  touch /var/www/html/.env
  echo "[entrypoint] APP_KEY set: $([ -n "$APP_KEY" ] && echo YES || echo NO)"
  php artisan config:cache
  exec "$@"

  RÔLE : s'exécute à chaque démarrage du conteneur app.
  Il injecte la config (APP_KEY etc.) passée via les variables d'env du
  docker-compose.prod.yml, puis lance php-fpm.
  IMPORTANT : sans "touch .env", Laravel refuse de démarrer même si toute
  la config est passée via variables d'environnement.


────────────────────────────────────────────────────────────────────────────────
6. DOCKER/PHP/PHP.INI ET OPCACHE.INI
────────────────────────────────────────────────────────────────────────────────

  php.ini (minimal pour la prod) :
      upload_max_filesize = 50M
      post_max_size = 52M
      memory_limit = 256M
      max_execution_time = 60

  opcache.ini (performances PHP) :
      opcache.enable=1
      opcache.memory_consumption=128
      opcache.interned_strings_buffer=8
      opcache.max_accelerated_files=10000
      opcache.revalidate_freq=0
      opcache.validate_timestamps=0

7. DOCKER-COMPOSE.PROD.YML
────────────────────────────────────────────────────────────────────────────────

  Ce fichier est utilisé directement par Hostinger pour lancer les conteneurs.
  Il référence les images pré-buildées sur GHCR (pas de build local sur le VPS).

  services:
    app:
      image: ghcr.io/TON_USER/TON_PROJET-app:latest
      restart: unless-stopped
      environment:
        APP_NAME: "MON_APP"
        APP_ENV: production
        APP_DEBUG: "false"
        APP_URL: ${APP_URL}
        APP_KEY: ${APP_KEY}
        LOG_CHANNEL: stderr
        LOG_LEVEL: error
        CACHE_DRIVER: file
        SESSION_DRIVER: file
        QUEUE_CONNECTION: sync
      volumes:
        - media_photos:/var/www/html/public/photos
        - media_videos:/var/www/html/public/videos
        - app_storage:/var/www/html/storage
      networks:
        - backend

    nginx:
      image: ghcr.io/TON_USER/TON_PROJET-nginx:latest
      restart: unless-stopped
      labels:
        - "traefik.enable=true"
        - "traefik.http.routers.monapp.rule=Host(`mondomaine.com`) || Host(`www.mondomaine.com`)"
        - "traefik.http.routers.monapp.entrypoints=websecure"
        - "traefik.http.routers.monapp.tls.certresolver=letsencrypt"
        - "traefik.http.services.monapp.loadbalancer.server.port=80"
      volumes:
        - media_photos:/var/www/html/public/photos:ro
        - media_videos:/var/www/html/public/videos:ro
      depends_on:
        - app
      networks:
        - backend

  volumes:
    media_photos:
    media_videos:
    app_storage:

  networks:
    backend:

  POINTS IMPORTANTS :
  - Les volumes media_photos / media_videos persistent entre les déploiements.
    Cela signifie que les médias uploadés sur le serveur ne sont PAS écrasés
    quand on redéploie. C'est voulu.
  - Traefik gère le HTTPS automatiquement via Let's Encrypt (voir section 9).
  - Le conteneur nginx n'a pas de port exposé directement : Traefik fait le
    routage depuis l'extérieur.


────────────────────────────────────────────────────────────────────────────────
8. GITHUB ACTIONS - .GITHUB/WORKFLOWS/DEPLOY.YML
────────────────────────────────────────────────────────────────────────────────

  Ce fichier se déclenche automatiquement à chaque push sur la branche main.
  Il fait 2 choses :
    1. Build les images Docker et les pousse sur GHCR
    2. Déclenche le déploiement sur le VPS Hostinger

  name: Deploy

  on:
    push:
      branches: [main]

  jobs:
    build-push:
      runs-on: ubuntu-latest
      permissions:
        contents: read
        packages: write

      steps:
        - uses: actions/checkout@v4
        - uses: docker/setup-buildx-action@v3

        - name: Login to GHCR
          uses: docker/login-action@v3
          with:
            registry: ghcr.io
            username: ${{ github.actor }}
            password: ${{ secrets.GITHUB_TOKEN }}

        - name: Build and push app (PHP-FPM)
          uses: docker/build-push-action@v6
          with:
            context: .
            target: app
            push: true
            tags: ghcr.io/TON_USER/TON_PROJET-app:latest
            cache-from: type=gha,scope=mon-app
            cache-to: type=gha,mode=max,scope=mon-app

        - name: Build and push nginx
          uses: docker/build-push-action@v6
          with:
            context: .
            target: nginx
            push: true
            tags: ghcr.io/TON_USER/TON_PROJET-nginx:latest
            cache-from: type=gha,scope=mon-nginx
            cache-to: type=gha,mode=max,scope=mon-nginx

    deploy:
      runs-on: ubuntu-latest
      needs: build-push

      steps:
        - uses: actions/checkout@v4

        - name: Deploy to Hostinger VPS
          uses: hostinger/deploy-on-vps@v2
          with:
            api-key: ${{ secrets.HOSTINGER_API_KEY }}
            virtual-machine: ${{ vars.HOSTINGER_VM_ID }}
            github-token: ${{ secrets.GITHUB_TOKEN }}
            project-name: mon-projet
            docker-compose-path: docker-compose.prod.yml
            environment-variables: |
              APP_KEY=${{ secrets.APP_KEY }}
              APP_URL=https://mondomaine.com
              DOMAIN=mondomaine.com

9. TRAEFIK (REVERSE PROXY + HTTPS AUTOMATIQUE)
────────────────────────────────────────────────────────────────────────────────

  Traefik tourne en permanence sur le VPS et intercepte tout le trafic entrant.
  Il route automatiquement vers le bon conteneur selon le domaine,
  et génère/renouvelle les certificats SSL Let's Encrypt tout seul.

  Sur Hostinger, Traefik est souvent pré-configuré. Si ce n'est pas le cas,
  voici le docker-compose.traefik.yml à déployer UNE FOIS sur le VPS :

  version: "3.8"
  services:
    traefik:
      image: traefik:v3.0
      restart: unless-stopped
      command:
        - "--api.insecure=false"
        - "--providers.docker=true"
        - "--providers.docker.exposedByDefault=false"
        - "--entrypoints.web.address=:80"
        - "--entrypoints.websecure.address=:443"
        - "--certificatesresolvers.letsencrypt.acme.httpchallenge=true"
        - "--certificatesresolvers.letsencrypt.acme.httpchallenge.entrypoint=web"
        - "--certificatesresolvers.letsencrypt.acme.email=TON@EMAIL.COM"
        - "--certificatesresolvers.letsencrypt.acme.storage=/letsencrypt/acme.json"
        # Redirige HTTP → HTTPS automatiquement
        - "--entrypoints.web.http.redirections.entrypoint.to=websecure"
        - "--entrypoints.web.http.redirections.entrypoint.scheme=https"
      ports:
        - "80:80"
        - "443:443"
      volumes:
        - "/var/run/docker.sock:/var/run/docker.sock:ro"
        - "letsencrypt:/letsencrypt"
      networks:
        - backend

  volumes:
    letsencrypt:
  networks:
    backend:
      external: true

10. SECRETS ET VARIABLES GITHUB À CONFIGURER
────────────────────────────────────────────────────────────────────────────────

  Dans GitHub → repo → Settings → Secrets and variables → Actions :

  SECRETS (valeurs sensibles) :
  ┌─────────────────────────┬────────────────────────────────────────────────┐
  │ Nom                     │ Valeur                                         │
  ├─────────────────────────┼────────────────────────────────────────────────┤
  │ APP_KEY                 │ La clé Laravel (php artisan key:generate)      │
  │ HOSTINGER_API_KEY       │ Clé API générée dans le panel Hostinger        │
  └─────────────────────────┴────────────────────────────────────────────────┘

  VARIABLES (valeurs non sensibles) :
  ┌─────────────────────────┬────────────────────────────────────────────────┐
  │ Nom                     │ Valeur                                         │
  ├─────────────────────────┼────────────────────────────────────────────────┤
  │ HOSTINGER_VM_ID         │ L'ID de ta VM (visible dans le panel Hostinger)│
  └─────────────────────────┴────────────────────────────────────────────────┘

  Comment générer l'APP_KEY :
    php artisan key:generate --show
  → copie la valeur "base64:..." et la coller dans le secret APP_KEY

  Comment obtenir la HOSTINGER_API_KEY :
    Panel Hostinger → VPS → API → Create API token

12. WORKFLOW QUOTIDIEN — COMMENT DÉPLOYER UNE MISE À JOUR
────────────────────────────────────────────────────────────────────────────────

  1. Faire ses modifications en local
  2. Tester en local (php artisan serve ou laragon)
  3. git add <fichiers modifiés>
  4. git commit -m "description du changement"
  5. git push origin main

  → GitHub Actions se déclenche automatiquement
  → Build Docker (~2-4 min avec cache, ~6-10 min sans cache)
  → Déploiement sur Hostinger (~1 min)
  → Le site est mis à jour

  Pour vérifier l'état du déploiement :
    GitHub → repo → Actions → voir le workflow en cours

13. ERREURS COMMISES ET À NE PLUS REFAIRE
────────────────────────────────────────────────────────────────────────────────

  ❌ ERREUR 1 — Committer un fichier vidéo lourd dans Git
  ─────────────────────────────────────────────────────────
  Problème : bk.mp4 (296 Mo) a été ajouté dans Git et pushé.
             GitHub bloque les fichiers > 100 Mo → le push échoue.
             Même après avoir effacé le fichier, il reste dans l'historique Git
             et continue de bloquer.

  Solution appliquée :
    git reset --soft origin/main
    (efface les commits locaux non pushés sans perdre les modifications)
    Puis re-committer uniquement les bons fichiers, sans la vidéo.

  Prévention : TOUJOURS ajouter les dossiers médias dans .gitignore AVANT
               de faire le premier commit. Ne jamais faire "git add ." en aveugle.

  ❌ ERREUR 2 — .gitignore corrompu
  ─────────────────────────────────
  Problème : le fichier .gitignore avait des espaces entre chaque caractère
             (ex: "p u b l i c / b k . m p 4") ce qui le rendait invalide.
             Git ignorait donc les règles.

  Cause probable : copie-colle depuis un éditeur ou un outil qui a mal encodé.
  Solution : réécrire le fichier .gitignore entièrement depuis zéro.

  ❌ ERREUR 3 — Chemin des médias différent entre local et prod
  ──────────────────────────────────────────────────────────────
  Problème : en local, bk.mp4 était dans public/ et référencé avec asset('bk.mp4').
             En production, Docker monte un volume sur public/videos/.
             Résultat : la vidéo de fond ne se chargeait pas en prod.

  Solution : toujours utiliser asset('videos/bk.mp4') et s'assurer que la
             structure de dossiers est identique entre local et prod.
             Les volumes Docker doivent correspondre exactement aux chemins
             utilisés dans le code.

  ❌ ERREUR 4 — PHP artisan view:clear ne suffit pas toujours
  ───────────────────────────────────────────────────────────
  Problème : après des modifications Blade, les anciennes vues compilées
             persistent même après "php artisan view:clear".

  Solution fiable (Windows/PowerShell) :
    Remove-Item -Recurse -Force storage\framework\views\*
  Ou (bash) :
    rm -rf storage/framework/views/*

  En production Docker, redémarrer le conteneur app recompile les vues :
    docker compose restart app

  ❌ ERREUR 5 — PowerShell ne supporte pas && pour chaîner des commandes
  ───────────────────────────────────────────────────────────────────────
  Problème : "php artisan view:clear && php artisan cache:clear" retourne
             une erreur de syntaxe dans PowerShell.

  Solution : utiliser le point-virgule ou exécuter les commandes séparément :
    php artisan view:clear ; php artisan cache:clear
  Ou utiliser le terminal Git Bash à la place de PowerShell.

  ❌ ERREUR 6 — Médias locaux non disponibles dans le conteneur Docker
  ──────────────────────────────────────────────────────────────────────
  Problème : en production, les dossiers public/photos et public/videos sont
             des volumes Docker vides au premier démarrage.
             Les médias doivent être uploadés manuellement ou via SCP/SFTP
             directement dans le volume sur le VPS.

  Comment uploader des médias sur le VPS :
    scp -r ./public/photos user@IP_VPS:/var/lib/docker/volumes/NOM_PROJET_media_photos/_data/
    scp -r ./public/videos user@IP_VPS:/var/lib/docker/volumes/NOM_PROJET_media_videos/_data/

  Le nom du volume Docker suit le pattern : NOM_PROJET_NOM_VOLUME
  (ex: saaheem_media_photos)


────────────────────────────────────────────────────────────────────────────────
14. CHECKLIST POUR UN NOUVEAU PROJET LARAVEL
────────────────────────────────────────────────────────────────────────────────

  □ Créer le repo GitHub (public ou privé)
  □ Configurer .gitignore avant le premier commit (vendor, node_modules, .env, médias)
  □ Créer le Dockerfile multi-stage (node-build → app → nginx)
  □ Créer docker/nginx/default.conf
  □ Créer docker/php/entrypoint.sh (chmod +x !)
  □ Créer docker/php/php.ini et opcache.ini
  □ Créer docker-compose.yml (pour test local)
  □ Créer docker-compose.prod.yml (pour Hostinger, images GHCR)
  □ Créer .github/workflows/deploy.yml
  □ Vérifier que le Dockerfile remplace TON_USER/TON_PROJET par les vrais noms
  □ Générer APP_KEY : php artisan key:generate --show
  □ Ajouter les secrets GitHub : APP_KEY, HOSTINGER_API_KEY
  □ Ajouter la variable GitHub : HOSTINGER_VM_ID
  □ S'assurer que Traefik tourne sur le VPS avec le réseau "backend" external
  □ Vérifier que le domaine pointe vers l'IP du VPS (DNS propagation ~24h)
  □ Faire le premier push sur main et surveiller GitHub Actions
  □ Uploader les médias sur le VPS via SCP après le premier déploiement


────────────────────────────────────────────────────────────────────────────────
15. COMMANDES UTILES EN PRODUCTION (sur le VPS via SSH)
────────────────────────────────────────────────────────────────────────────────

  # Voir les conteneurs qui tournent
  docker ps

  # Voir les logs en temps réel
  docker compose logs -f

  # Redémarrer l'app (recharge la config)
  docker compose restart app

  # Vider le cache Laravel dans le conteneur
  docker compose exec app php artisan cache:clear
  docker compose exec app php artisan view:clear
  docker compose exec app php artisan config:cache

  # Lister les volumes et leur emplacement
  docker volume ls
  docker volume inspect NOM_DU_VOLUME

  # Mettre à jour manuellement les images (sans passer par GitHub Actions)
  docker compose -f docker-compose.prod.yml pull
  docker compose -f docker-compose.prod.yml up -d
